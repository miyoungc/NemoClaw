## Manage Dashboard Ports

If a managed forward stopped or the URL does not load, restore its identity-bound lifecycle through NemoClaw.

```bash
nemoclaw my-gpt-claw recover
```

For lower-level diagnostics, list OpenShell's legacy and user-managed forwards separately. Receipt-owned ForwardTcp services are verified by `nemoclaw <name> status` and `recover`.

```bash
openshell forward list
```

</AgentOnly>

## Run Multiple Sandboxes

Choose a distinct sandbox name of 1 to 19 characters before onboarding.
The limit matches OpenShell's routed sandbox-name limit and applies to every agent runtime.
For the complete naming rules, refer to [`onboard --name`](../../reference/commands#--name-sandbox).

<AgentOnly variant="openclaw,hermes">
Each sandbox needs its own dashboard port because `openshell forward` refuses to bind a port that another sandbox already uses.
</AgentOnly>

<AgentOnly variant="deepagents">
Deep Agents sandboxes do not expose a dashboard port.
The first `nemo-deepagents onboard` run can use the default sandbox name from the wizard.
When you create another Deep Agents sandbox, choose a distinct sandbox name in the wizard or pass `--name` in scripted runs.
</AgentOnly>

<AgentOnly variant="openclaw">
When the default port is already held by another sandbox, `$$nemoclaw onboard` scans ports `18789` through `18799` and uses the next verified available port.
</AgentOnly>

<AgentOnly variant="hermes">
Each Hermes sandbox also needs its own OpenAI-compatible API port.
When creating a Hermes sandbox, if another sandbox or a host listener already holds the default API port `8642`, `$$nemoclaw onboard` scans ports `8642` through `8652`, uses the next verified available port, and records it for the sandbox.
</AgentOnly>

<AgentOnly variant="openclaw,hermes">
When allocating ports for a new sandbox, NemoClaw skips candidates whose OpenShell forward ownership cannot be verified.
It can select a later candidate only when that port is verified available.
If no candidate is available, the error lists each blocked port, including a preferred dashboard port outside the default range.
When every candidate has unverified ownership, inspect ownership before rerunning onboarding.
For mixed failures, the error includes both verification recovery and the existing occupied-port remedies.
Refer to [Port already in use](../../reference/troubleshooting#port-already-in-use) for those recovery actions.
</AgentOnly>

<AgentOnly variant="openclaw,hermes">
If you intentionally run separate OpenShell gateways on the same host, set a different `NEMOCLAW_GATEWAY_PORT` before each onboarding run.
NemoClaw isolates the gateway name and local state by port so one port-specific gateway does not replace another.
Sandbox-scoped commands, including `exec`, `status`, `start`, and `stop`, address the sandbox through its recorded gateway binding. `NEMOCLAW_GATEWAY_PORT` selects the gateway for onboarding and new gateway-scoped setup; it does not redirect an existing sandbox command.
A non-default `NEMOCLAW_GATEWAY_PORT` also gets its own host state root at `~/.nemoclaw/gateways/<port>/`, with a separate sandbox registry, rebuild backups, and legacy credential-migration files, so gateway-scoped state stays segregated while shared host-level files remain under `~/.nemoclaw/`.
On first use after upgrading, NemoClaw moves legacy rows and related state only when their recorded gateway identity matches the selected port; ambiguous state is left untouched with remediation.
Provider credentials remain in the OpenShell gateway store.
The default port keeps the shared `~/.nemoclaw/` location.
When other ports remain, `$$nemoclaw uninstall` removes only the selected gateway and keeps the shared CLI, services, images, providers, configuration, models, and swap.

Gateway and dashboard cleanup is scoped by sandbox name and port.
A later onboarding run that uses a different `NEMOCLAW_GATEWAY_PORT` or `--control-ui-port` does not tear down the first sandbox's gateway or dashboard forward.
</AgentOnly>

<AgentOnly variant="openclaw,hermes">
Repeated onboarding and resume keep the sandbox's registered dashboard port and restore a missing forward on that port.
If the port is already bound, NemoClaw verifies that the listener is the exact OpenShell forward for that sandbox and reuses it without restarting the sandbox.
For that registered port, another sandbox's registration, a foreign listener, or unverified ownership still stops onboarding with a port conflict error.
</AgentOnly>

<AgentOnly variant="hermes">
Hermes also retains or restores its registered OpenAI-compatible API forward using the same ownership checks.
</AgentOnly>

<AgentOnly variant="deepagents">
If you intentionally run separate OpenShell gateways on the same host, set a different `NEMOCLAW_GATEWAY_PORT` before each onboarding run.
NemoClaw isolates the gateway name and local state by port so one port-specific gateway does not replace another.

A non-default `NEMOCLAW_GATEWAY_PORT` also gets its own host state root at `~/.nemoclaw/gateways/<port>/`, with a separate sandbox registry, rebuild backups, and legacy credential-migration files, so gateway-scoped state stays segregated while shared host-level files remain under `~/.nemoclaw/`.
On first use after upgrading, NemoClaw moves legacy rows and related state only when their recorded gateway identity matches the selected port; ambiguous state is left untouched with remediation.
Provider credentials remain in the OpenShell gateway store.
The default port keeps the shared `~/.nemoclaw/` location.
When other ports remain, `nemo-deepagents uninstall` removes only the selected gateway and keeps the shared CLI, services, images, providers, configuration, models, and swap.
Gateway cleanup is scoped by sandbox name and port.
</AgentOnly>

<AgentOnly variant="openclaw,hermes">

```bash
$$nemoclaw onboard                                      # first sandbox uses 18789 when verified available
$$nemoclaw onboard                                      # second sandbox uses the next verified available port, such as 18790
```

To choose a specific port, pass `--control-ui-port`:

```bash
$$nemoclaw onboard --control-ui-port 19000
```

You can also set `CHAT_UI_URL` or `NEMOCLAW_DASHBOARD_PORT` before onboarding:

```bash
CHAT_UI_URL=http://127.0.0.1:19000 $$nemoclaw onboard
NEMOCLAW_DASHBOARD_PORT=19000 $$nemoclaw onboard
```

For port conflicts and overrides, refer to [Port already in use](../../reference/troubleshooting#port-already-in-use).

</AgentOnly>

```bash
nemo-deepagents onboard
# For an additional named sandbox:
nemo-deepagents onboard --name <sandbox-name>
```

## Stop and Start a Sandbox

Stop a sandbox through OpenShell to free CPU, memory, and GPU resources without losing anything:

```bash
$$nemoclaw <sandbox-name> stop
```

Workspace files, credentials, network policies, and the registry entry are preserved.
OpenShell stops the sandbox's provider workload.
<AgentOnly variant="openclaw,hermes">
After the sandbox stops, NemoClaw attempts to stop that sandbox's host dashboard forward.
The shared host gateway and tunnel services keep serving other sandboxes.
</AgentOnly>

Start it again later:

```bash
$$nemoclaw <sandbox-name> start
```

<AgentOnly variant="openclaw,hermes">
After OpenShell accepts the start, NemoClaw waits for it to report the sandbox in the `Ready` or `Running` state.
NemoClaw recovers missing agent processes and host forwards only after that phase, so a slow sandbox start does not need a separate `recover` command.
</AgentOnly>
<AgentOnly variant="deepagents">
After OpenShell accepts the start, NemoClaw waits for it to report the sandbox in the `Ready` or `Running` state, then verifies the managed terminal runtime before the command reports success.
</AgentOnly>
Refer to [`$$nemoclaw <name> stop`](../../reference/commands#$$nemoclaw-name-stop) and [`$$nemoclaw <name> start`](../../reference/commands#$$nemoclaw-name-start) for details.
Use [`$$nemoclaw <name> destroy`](../../reference/commands#$$nemoclaw-name-destroy) when you want to delete the sandbox instead.

## Manage the Cloudflare Tunnel

When the host has `cloudflared`, `$$nemoclaw tunnel start` starts a Cloudflare tunnel.
The tunnel can expose the dashboard with a public URL.
NemoClaw manages one tunnel for the selected OpenShell gateway port, independent of individual sandbox lifecycles.
Stopping, destroying, or recreating a sandbox does not stop that tunnel.
Set `CLOUDFLARE_TUNNEL_TOKEN` before running the command when you want to use a Cloudflare named tunnel instead of a generated quick-tunnel URL.
If command-line inspection is unavailable, Windows can still verify and stop a recorded `cloudflared.exe` through an identity-bound process handle. Other platforms require process inspection before signaling. If NemoClaw cannot verify the process identity or stop it safely, it refuses to create a second tunnel; restore inspection access or independently verify and stop the process before retrying. [`$$nemoclaw tunnel status`](../../reference/commands#$$nemoclaw-tunnel-status) reports this recovery state.

```bash
$$nemoclaw tunnel start
```

`$$nemoclaw tunnel stop` stops the tunnel and asks NemoClaw to stop the in-sandbox gateway for the selected or default sandbox.
An explicitly set `NEMOCLAW_GATEWAY_PORT` selects the host tunnel state.
Otherwise, tunnel commands use the selected or default sandbox's owning gateway, falling back to the process-default gateway when no sandbox resolves.
If the sandbox name belongs to more than one gateway registry, tunnel-state selection fails closed.
After an upgrade, when no live gateway-scoped PID record exists and exactly one live legacy PID record matches a sandbox in the selected gateway registry, NemoClaw moves that record into gateway-scoped state.
If NemoClaw cannot inspect that PID's process identity, it preserves the record and refuses to start a second tunnel.
If multiple live PID records exist, the command reports the conflict and requires you to stop the unintended process through its process manager before starting a tunnel.
On non-Windows hosts, NemoClaw scans the current user's process list when no live managed tunnel record exists.
It reports an unrecorded `cloudflared` executable as a conflict.
Windows skips this scan.
If process listing fails on another platform, tunnel start fails closed without starting a tunnel, and status cannot report unmanaged conflicts until process inspection is restored.
If NemoClaw reports incomplete tunnel cleanup, independently verify and stop the recorded cloudflared process with the host process manager, keep the PID record until that process exits, then retry the command.
The older `$$nemoclaw start` now prints migration guidance and exits successfully without starting
a sandbox or tunnel. Use `$$nemoclaw <name> start` or `$$nemoclaw tunnel start` explicitly.
</AgentOnly>

## Run an OpenClaw Task from a Shell Script

Use NemoClaw from a host Bash script to submit a task file, save the response, and check the requested result.
You need an existing OpenClaw sandbox in the `Ready` or `Running` phase and an available OpenShell executable.
Confirm readiness with `nemoclaw <sandbox-name> status` before running the script.
Choose an existing agent ID, or use another target selector: `--session-id`, `--session-key`, or `--to`.
Run `openclaw agents list` inside the sandbox if you need to find an agent ID.
The example also requires Node.js on the host for its JSON acceptance check.
For command options, refer to the [agent command reference](../../reference/commands#$$nemoclaw-name-agent).

### Prepare Host-File Input

Redirect a host file into standard input without `-m`, `--message`, or `--message-file`.
The host shell reads the file and passes its contents to OpenClaw in the selected sandbox.
By contrast, `--message-file` names a file inside the sandbox; it does not upload a host file.
That sandbox file must exist and be readable by the in-sandbox process.
Relative message-file paths resolve inside the sandbox, not against your host working directory.

This procedure requires the managed OpenClaw parser's implicit-stdin support.
The checked-in patch targets OpenClaw `2026.9.2`; do not assume older or custom images contain it.
The managed parser requires nonblank, valid UTF-8 input and limits file or standard-input messages to 4 MiB.
A finite file supplies end-of-file automatically; a pipe producer must close its output after writing the message.
An explicit `--message` takes precedence over redirected input, and an empty explicit message fails instead of reading stdin.
Do not combine `--message` with `--message-file`.

### Save and Check the Result

Keep saved output private: raw stdout and stderr are not redacted, even when NemoClaw sanitizes added provenance diagnostics.
They can contain sensitive task or tool content.
The example creates a fresh private directory and retains the task, result, diagnostics, and command status on failure.
For real tasks, decide how to verify the requested outcome before dispatch; a retry can repeat changes already made.

Save the following script as `run-task.sh` and replace `my-assistant` and `main` with your sandbox name and agent ID.

```bash
#!/usr/bin/env bash
set -eu
umask 077

sandbox='my-assistant'
agent_id='main'
out_dir=$(mktemp -d "${TMPDIR:-/tmp}/nemoclaw-task.XXXXXXXX")
printf 'Saved files: %s\n' "$out_dir"
printf '%s\n' 'What is 2 + 2? Reply with only 4. Do not use tools.' > "$out_dir/task.txt"

if nemoclaw "$sandbox" agent --agent "$agent_id" --json --timeout 120 \
    < "$out_dir/task.txt" > "$out_dir/result.json" 2> "$out_dir/diagnostics.log"; then
  command_status=0
else
  command_status=$?
fi
printf '%s\n' "$command_status" > "$out_dir/command-status.txt"

if [ "$command_status" -ne 0 ]; then
  printf 'Command failed with status %s. Inspect saved files before retrying.\n' \
    "$command_status" >&2
  exit "$command_status"
fi

if node - "$out_dir/result.json" <<'NODE'
const fs = require('node:fs');
const record = (value) => value !== null && typeof value === 'object' && !Array.isArray(value);
try {
  const doc = JSON.parse(fs.readFileSync(process.argv[2], 'utf8'));
  if (!record(doc) || 'event' in doc) throw new Error();
  let response;
  if ('result' in doc) {
    if (doc.status !== 'ok' || 'payloads' in doc || 'meta' in doc) throw new Error();
    response = doc.result;
  } else {
    if ('status' in doc) throw new Error();
    response = doc;
  }
  if (!record(response) || !record(response.meta)) throw new Error();
  if (response.meta.aborted === true || response.meta.error !== undefined) throw new Error();
  const payloads = response.payloads;
  if (!Array.isArray(payloads) || payloads.length !== 1) throw new Error();
  const reply = payloads[0];
  if (!record(reply) || reply.isError === true || typeof reply.text !== 'string' ||
      reply.text.trim() !== '4') throw new Error();
} catch {
  console.error('Acceptance check failed: expected one JSON response with one reply containing only 4.');
  process.exit(1);
}
NODE
then
  printf 'Acceptance check passed: the reply is 4.\n'
else
  printf 'Inspect saved files before retrying.\n' >&2
  exit 1
fi
```

Run the script from your host shell.

```bash
bash run-task.sh
```

The script captures the command status immediately, including nonzero status under `set -e`.
It accepts only status zero plus one reply containing `4`, allowing surrounding whitespace.
It checks either the gateway response's `result.payloads` or the local response shape's `payloads`; it does not enable `--local` mode.
Missing, malformed, log-prefixed, ambiguous, or unexpected output fails this acceptance check and remains saved for inspection.
This check verifies only the arithmetic answer, not completion of an arbitrary task.
For tasks that change resources, check those resources rather than trusting a success envelope or a nonempty result file.

NemoClaw buffers the dispatched command's stdout and stderr until dispatch completes, so the files are not live progress streams.
The streams share a 64 MiB capture limit.
On overflow, NemoClaw reports failure, sends `SIGTERM` to the running OpenShell child, and retains only chunks captured before the overflow.
The overflowing chunk and subsequent chunks are discarded; the saved result can be partial or invalid JSON.
With `--json`, NemoClaw preserves captured stdout rather than repairing malformed or log-prefixed output.
It writes captured stderr and added provenance diagnostics to the diagnostic stream.

Tool-failure diagnostics can accompany exit status zero.
Recognized incomplete-turn metadata can instead change upstream status zero to status one, after the available trace is written.
Neither valid JSON nor exit status zero alone proves task success.
If diagnostics identify untrusted child output, verify that data before using it.

### Inspect Failures Before Retrying

Keep both output files after a failure, including an acceptance-check failure.
Inspect `diagnostics.log` and `result.json` before changing options.
For an incomplete or timed-out turn, locate the session key with the following command.

```bash
nemoclaw <sandbox-name> sessions list
```

Export the selected session's transcript with its key.

```bash
nemoclaw <sandbox-name> sessions export <key>
```

Inspect the transcript and affected resources before another attempt.
A timeout or abandoned turn does not establish rollback: tool calls can already have applied changes.
Do not add automatic retries without checking those effects.

### Troubleshoot the Timeout Phase

Identify which wait failed before increasing a deadline.
The following table distinguishes the input, turn, transport, and provider waits.

| Wait | What to Check |
| --- | --- |
| Input | For `Timed out waiting for stdin`, first confirm that the producer closes its output. The managed parser defaults to 30 seconds and uses a finite positive supplied timeout instead, capped at 2,147,483,647 milliseconds. This timer starts in the parser, not before remote dispatch. |
| Agent turn | Use a positive whole-number `--timeout`, such as the example's `120`. NemoClaw's diagnostic identifies `agents.defaults.timeoutSeconds` as the run deadline and `agent --timeout <seconds>` as its per-run override. |
| OpenShell execution | NemoClaw requests an execution deadline of the forwarded turn timeout plus 30 seconds. This is not a total wall-clock bound on readiness checks or lock acquisition. |
| Provider request | When diagnostics report a provider timeout, inspect the deployed provider configuration. NemoClaw's diagnostic identifies `models.providers.<id>.timeoutSeconds` as a separate deadline with no flag override. Increasing `--timeout` is not a general fix for provider failures. |

For a recognized timeout, NemoClaw starts its command budget after readiness and selector checks.
When pre-dispatch Ollama recovery applies, it shares that budget and reserves one second for dispatch.
NemoClaw forwards the remaining turn budget rounded up, with a one-second minimum; the OpenShell deadline uses that forwarded value.
An absent, zero, malformed, or uninterpretable timeout does not request this transport deadline.
Neither does a timeout after `--` or an unrecognized option, unless NemoClaw already recognized an earlier valid timeout.
Values outside safe-integer arithmetic also cannot establish the transport bound.
These cases do not disable independent parser, agent, or provider deadlines.

Check the reported phase and actual sandbox configuration before adjusting a deadline.
The managed parser and NemoClaw diagnostics describe this implementation, not proof of the parser or provider behavior deployed in your sandbox.
